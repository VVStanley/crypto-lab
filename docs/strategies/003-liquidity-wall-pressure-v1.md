# Стратегия 003 — LiquidityWallPressureV1

Статус: **исследование / сбор данных**

Связанный эксперимент: `experiments/003-liquidity-wall-pressure.md`

## Идея простыми словами

Мы ищем в стакане BTC/USDT аномально крупные уровни ликвидности — «стенки» — и наблюдаем не просто их размер, а **борьбу цены с этой стенкой**.

Типичный пример вверх:

```text
цена растёт
    |
    v
крупная ASK-стенка
    |
покупатели начинают её исполнять
    |
    +-> стенка успевает восстанавливаться -> возможен отбой
    |
    +-> стенка быстрее истончается -> возможен пробой
```

Для движения вниз логика зеркальная относительно крупной BID-стенки.

Главная гипотеза:

> Вероятность пробоя или отбоя определяется не столько первоначальным размером стенки, сколько тем, как она ведёт себя под реальным потоком сделок: насколько быстро её исполняют, пополняют или снимают, двигается ли цена несмотря на объём и сколько ликвидности остаётся сразу за стенкой.

## Почему это может работать

Видимая крупная заявка сама по себе ненадёжна. Она может быть снята, дополнена другими участниками или представлять лишь видимую часть большей ликвидности.

Поэтому стратегия не делает вывод:

```text
большой ASK = цена обязательно упадёт
большой BID = цена обязательно вырастет
```

Вместо этого мы измеряем динамику.

### Кандидат на пробой ASK-стенки

```text
цена подходит к стенке
+
агрессивные BUY растут
+
реальные сделки проходят по цене стенки
+
стенка восстанавливается слабее, чем её исполняют
+
видимый объём уменьшается
+
цена всё лучше реагирует на покупки
+
за стенкой мало следующей ASK-ликвидности
```

Такое состояние может повышать вероятность движения вверх после пробоя.

### Кандидат на отбой от ASK-стенки

```text
агрессивных BUY много
+
по стенке проходит большой объём
+
но стенка постоянно восстанавливается
+
цена почти перестаёт продвигаться вверх
+
несколько атак уровня не дают результата
+
покупательский поток начинает слабеть
```

Это похоже на поглощение спроса продавцами и потенциальный rejection.

Для BID-стенок логика исследуется зеркально.

## Что такое «стенка» в наших данных

Публичный Binance Level-2 показывает агрегированное количество на price level, а не личность владельца и не список отдельных ордеров.

Поэтому мы не говорим:

```text
это кит
это маркет-мейкер
этот участник купил
```

Корректная формулировка:

> На данном уровне цены находится аномально большой видимый агрегированный объём.

Стенка определяется относительно текущего рынка, а не фиксированной суммой долларов.

Например учитываются:

```text
notional уровня
отношение к соседним уровням
локальный percentile/rank
доля ближайшей глубины
расстояние от mid-price
```

## Какие данные нужны

Первая версия использует только Binance Spot BTC/USDT:

```text
diff depth @ 100 ms
aggTrade
REST depth snapshot для синхронизации
```

Нам нужны одновременно стакан и реальные сделки.

Если видимый объём уровня уменьшился, одного depth-stream недостаточно, чтобы понять, был ли он исполнен или просто снят.

Сопоставление depth changes и aggTrades позволяет оценивать:

```text
observed execution
estimated refill
estimated withdrawal
```

Последние два показателя являются оценками, а не точным знанием поведения отдельного участника.

## Что измеряем

### Размер и жизнь стенки

```text
initial_notional
peak_notional
current_notional
relative_size
wall_age
```

### Подход цены

```text
distance_to_wall_bps
approach_velocity
approach_growth_ratio
```

`approach_growth_ratio` помогает описать наблюдение, когда стенка увеличивается по мере приближения цены.

### Насколько стенку реально едят

```text
executed_against_wall
execution_rate
wall_depletion
depletion_rate
```

### Насколько она восстанавливается

```text
estimated_refill
refill_rate
refill_ratio
```

Условно:

```text
refill_ratio << 1
-> исполнение быстрее восстановления

refill_ratio >= 1
-> стенка восстанавливается не хуже, чем её едят
```

Это только интерпретация для исследования; реальные пороги заранее не считаются доказанными.

### Снятие ликвидности

```text
estimated_withdrawal
```

Важно отличать ситуацию:

```text
стенку съели сделками
```

от:

```text
стенка исчезла из-за снятия видимого объёма
```

### Агрессивный поток сделок

```text
aggressive BUY / SELL 1s
aggressive BUY / SELL 5s
aggressive BUY / SELL 15s
aggressive BUY / SELL 60s
trade-flow imbalance
```

### Реакция цены

Очень важный признак — сколько движения цены получается из большого агрессивного объёма.

```text
много BUY + сильный рост
```

и

```text
много BUY + цена почти стоит
```

имеют разный смысл.

Второй вариант может быть признаком absorption.

### Что находится за стенкой

После разрушения крупного уровня важно знать, насколько плотная следующая ликвидность.

Исследуем:

```text
post-wall liquidity
liquidity gap behind wall
multi-level imbalance
```

Если сразу за разрушенной стенкой стакан тонкий, движение потенциально может ускориться.

## Как выглядит исследовательский event

Одна стенка не должна превращаться в сотни независимых строк только потому, что стакан обновляется каждые 100 ms.

Мы рассматриваем её как одну кампанию:

```text
CANDIDATE
    -> APPROACHING
    -> UNDER_ATTACK
    -> BREAKOUT / REJECTION / DISAPPEARED / EXPIRED
```

Это позволяет честно считать статистику по рыночным эпизодам.

## Как будем проверять идею

Сначала система вообще не торгует.

Она собирает raw data и затем офлайн строит:

```text
стакан
-> стенки
-> атаки стенок
-> pressure/refill/absorption features
-> будущие движения цены
```

Для каждого подходящего события позже считаются, например:

```text
future return 5s
future return 15s
future return 60s
future return 5m
maximum movement through wall
maximum rejection movement
time to first cross
time spent beyond wall
```

Исследование сравнивает не только красивые пробои, но и все остальные похожие события.

Нас интересует вопрос:

> Если признаки X/Y/Z присутствуют, насколько вероятность и величина будущего движения отличаются от обычного wall-attack event?

## Что может оказаться сильным сигналом

Наиболее интересное сочетание для будущего анализа:

```text
агрессивный поток усиливается
+
стенка реально исполняется
+
refill слабеет относительно execution
+
стенка истончается
+
реакция цены усиливается
+
за стенкой мало ликвидности
```

Это кандидат на breakout pressure.

Обратный паттерн:

```text
агрессивного объёма много
+
стенка постоянно восстанавливается
+
цена почти не реагирует
+
атаки повторяются без продвижения
+
агрессивный поток истощается
```

— кандидат на rejection / absorption.

## Как предполагается входить

**Пока никак.**

На текущем этапе торговое правило намеренно не определено.

Если исследование подтвердит устойчивый эффект, отдельно будут сравнены как минимум:

```text
anticipatory breakout
-> вход до окончательного разрушения wall

confirmed breakout
-> wall пройдена и цена подтверждает движение
```

Для первой реальной реализации confirmed breakout вероятнее будет более понятным кандидатом, но это решение не должно приниматься до данных.

Поскольку проект сейчас Spot long-only, bearish-сигналы могут использоваться как запрет/выход из long, а не обязательно как short.

## Как предполагается выходить

Правила выхода, stoploss, breakeven и фиксации прибыли **не определены в этом experiment**.

Сначала должен быть доказан сам predictive signal вокруг wall events.

Execution/risk design будет отдельным этапом после Research/Validation.

## Ожидаемая частота

В отличие от медленной 4h TrendBreakoutV1, liquidity-wall events потенциально возникают много раз в течение дня.

Но реальная частота **не считается известной**, пока collector не накопит данные и detector не покажет количество независимых валидных campaigns.

Частота сама по себе не является преимуществом. Сигнал должен переживать spread, fees, latency и realistic execution.

## Основные риски идеи

1. **Большая видимая стенка может быть ложной или быстро снятой.**
2. **Публичный L2 не показывает личность и отдельные ордера.**
3. **Refill/withdrawal можно только оценивать по агрегированным данным.**
4. **Стакан меняется очень быстро; найденный эффект может жить слишком мало для обычного VPS execution.**
5. **Красивые визуальные примеры могут не иметь статистической силы.**
6. **Похожие признаки могут встречаться и перед пробоем, и перед отбоем.**
7. **Сигнал может исчезнуть после комиссий/spread/slippage.**
8. **Небольшая выборка легко создаёт ложное ощущение закономерности.**

Поэтому стратегия должна пройти хронологические Research / Validation / OOS периоды.

## Хранение и воспроизводимость

Исследовательский pipeline должен сохранять:

```text
raw Binance events -> immutable compressed files
features/events     -> Parquet
analysis            -> DuckDB SQL
```

Raw archive нужен для повторного построения рынка и признаков после изменения алгоритмов.

Аналитическая логика отделена через ports/DI, чтобы позже можно было добавить ClickHouse без переписывания domain logic.

## Краткая аналитика

Пока аналитики результатов нет, потому что experiment ещё не собирал собственный L2 dataset.

Первый значимый результат должен отвечать не на вопрос «сколько заработали», а на вопросы:

```text
сколько валидных wall campaigns наблюдается
какие признаки отличаются перед breakout/rejection
насколько велик subsequent move
сохраняется ли эффект во времени
достаточен ли он потенциально после costs/latency
```

## Что ещё неизвестно

- оптимальное определение wall candidate;
- реальная частота независимых wall attacks;
- какие features наиболее информативны;
- достаточно ли публичного Binance L2 для устойчивого signal;
- сколько времени живёт signal;
- существуют ли отличия между ASK/BID behavior;
- какой entry style будет реалистичным;
- как должен выглядеть risk/exit management;
- останется ли edge после реального исполнения.
